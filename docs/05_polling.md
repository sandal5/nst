# 轮询机制 / Polling design（13,528 个对象）

## 本项目的工作流（定版）
每个目标站都走同一条流水线，这也是当前阶段（收集信息阶段）的主线：

1. **找到目标站**（对象 → 官方网站）；
2. **找到入札公告的准确地址**——本阶段难度最大的一步：目录旧链接大面积过期，须在官网站内沿导航/站内检索定位到真正的公告列表页或電子調達系统公开页，并验证其现行有效；
3. **采样分析**该页面的 web 信息架构（列表结构、分页、日期与附件的组织方式、是否需 JS/会话）；
4. **记录**：准确地址、架构特征、规约状态、采样日期写入对象/端点注册表；
5. **分类**：归入框架类型 P1–P7（见 docs/02）；
6. **做分类采集器**：每类一个模版/adapter，部署形态为 Cloudflare Worker；
7. **指数回避轮询**（下一步重点）：见下节。


## 先把概念分清（Gordon 2026-10-27 定版）
- **KKJ 与另一目录源只是「一次性枚举」**：各访问一次，把全部发注对象找出来，仅此而已。之后**永不再访问这两个站**，更不是从它们采集。
- **采集对象 = 13,528 个发注对象本身**（KKJ 枚举 3,959 + 另一目录源枚举 9,569）。每个对象在自己的**官方网站**上发布公告，轮询就是逐对象回到其官网站取公告。
- 因此系统分两层：
  - **对象注册表（objects）**：13,528 行——对象名、都道府县、层级、上级对象、官方域名、数据源（kkj／另一目录源 一次性枚举）。文件：`data/objects_registry.csv`。
  - **轮询端点（endpoints）**：对象解析到的实际公告页 URL。文件：`data/endpoints.csv`。

## 为什么按端点轮询、而不是按对象（效率核心）
很多对象共用同一个公告页：省厅各出先机关共用本厅調達页；市町村参加县级電子調達共同系统；另一目录源里近半数是无独立官网的下级单位，其公告出现在上级对象页面上。
- KKJ 侧实测：3,971 个对象 → 3,381 个候选端点（2026-10-27 按已验证现行页重建），已有 107 个端点同时服务多个对象（697 个对象）。
- 待 P6 逐站定位与共同系统归并完成后，端点数还将显著下降（下级单位对象归并到上级端点）。
- 端点抓一次、解析一次，再按发注机关名把公告**归属**回该端点登记的各个对象——不重复抓取同一页面。

## 轮询引擎（worker/src/poll.js）
1. **指数回避轮询（核心）**：每个端点有自己的轮询间隔，按层级定起点与上限（A：12 小时起、上限 2 天；B：1 天起、上限 8 天；C：2 天起、上限 32 天）。**每轮询一次未发现变化，间隔 ×2**（带 ±10% 抖动防同步）；**一发现变化，立即重置回起点**。理由很实际：大量发注对象几个月才发一次公告，固定日轮询等于一年对同一个小市町村服务器发出 365 次注定无果的请求。指数回避后，一个季度发一次的 C 类端点轨迹是第 0、2、6、14、30、62、94 天……约 **12 次/年（省约 97%）**，而活跃端点仍保持高频；最坏发现延迟被层级上限封顶。失败（404/5xx/网络）同样指数退避 1→2→4 天，仍失败转「重新验证队列」回官网找新地址。实现：`worker/src/poll.js`（`growInterval` / `resetInterval`）。
2. **先判变、后解析**：条件请求（ETag / Last-Modified）+ 正文 SHA-256 哈希。未变化只记心跳，不解析、不下载附件——这是全量轮询省成本的关键。
3. **调度分片**：每小时 Cron 只做计划：把到期端点按「同主机不重复」打包成片（≤25/片）入 Queue，consumer 逐片执行；同主机请求间隔 ≥2 秒、单主机同时最多 1 个在途。
4. **失败退避**：404/5xx/网络错误按 1 天→3 天→7 天退避，仍失败则转入「重新验证队列」（去官网站找新页面），不反复敲打；403/429 当日停该主机并标记人工处理。
5. **门禁不变**：robots 禁止、规约未确认（terms_status 非 verified）、P6 未定位到列表页的端点，一律跳过并登记原因，绝不硬抓。
6. **状态留痕**：每端点保存 last_polled / last_changed / etag / hash / failures / tier（D1 `endpoints` 表规划见 schema），每条公告保存来源端点与归属对象，可追溯可纠错。

## 规模与预算估算（端点归并后的工作假设，非实测）
- 端点 ~3,500 时：A≈1,500 每日 + B≈1,200/3 日 + C≈800/7 日 ≈ **每日约 2,000 次列表页请求**，其中多数会被 304/哈希判为未变化；只有变化的端点才进一步解析和下载新公告 PDF。
- 该量级在 Cloudflare Workers（Paid）+ Queues + D1 的配额内可平稳运行；免费层适合小规模试点（如先跑通 47 个都道府县级端点）。

## 未决站点的打捞轮询（指数退避）

连接错误、人工未确定等未决站点不做固定周期重扫，沿用指数退避思想管理打捞节奏（2026-10-28 定版：边际收获越小，周期越长）：

- 队列维度：每轮全量尝试未决队列后，按本轮回收率决定下一轮间隔——回收率 ≥20% 间隔 1 周；5%–20% 间隔 2 周；1%–5% 间隔 4 周；<1% 间隔 8 周，其后每轮翻倍直至季度级封顶。
- 单站维度：连续多轮未回收的站点，其下一次尝试间隔同样逐轮翻倍；一旦回收，立即退出打捞队列转入正常端点轮询。
- robots 禁止不适用自动打捞（合规红线），只走人工确认或截图核验路线。
